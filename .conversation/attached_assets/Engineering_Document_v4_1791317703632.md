الوثيقة الهندسية الشاملة — النسخة ٤.٠
تُدمج بهذه النسخة: (أ) حصر نطاق التنفيذ الفعلي بالخطة الفردية مع تصنيف معماري ثلاثي للقدرات المستقبلية (نشطة/كامنة/مستقبلية) وفئة رابعة للقرارات المرفوضة، و(ب) إعادة تموضع بصمة الأسلوب وما حولها كمحرك ذكاء أستاذ مستقل (Instructor Intelligence Engine) بعقد إخراج موحّد. كل تعديل موثَّق بمكانه مع الإبقاء على ترقيم الأقسام الأصلي.
## ٠. ملخص تنفيذي وموقع هذه الوثيقة
هذه الوثيقة هي إعادة بناء كاملة للنسخة الأولى، وليست تعليقاً عليها. النسخة الأولى كانت بداية سليمة: حددت مشكلة حقيقية (استهلاك وقت الأستاذ بإعداد أسئلة امتحان)، ورفضت بحق البناء فوق NotebookLM، وحسبت تكلفة الذكاء الاصطناعي بشكل واقعي. لكنها تعاملت مع المشروع كأداة (Tool) بميزة واحدة (بصمة الأسلوب)، بينما القيمة الحقيقية طويلة الأمد تكمن في أن يصبح المشروع نظام معرفة أكاديمي يملك بيانات لا يملكها أي منافس: تاريخ الأسئلة، خرائط المنهج، وسلوك المراجعة البشرية لكل أستاذ ومادة عبر فصول متعددة.

## ٢. إعادة بناء الرؤية: من 'مولّد أسئلة' إلى 'منصة ذكاء المساق الأكاديمي'
الرؤية الأصلية صحيحة كنقطة انطلاق لكنها ضيقة كوجهة نهائية. أداة توليد أسئلة هي ميزة، ليست منصة. المنافس الذي يملك فريق أكبر ورأس مال أكبر يمكنه نسخ ميزة توليد الأسئلة خلال أسابيع. ما لا يمكنه نسخه بسهولة هو تراكم بيانات المساق عبر فصول دراسية متعددة مع نفس الأستاذ.
الـPivot المقترح (تدريجي لا فوري): المنتج يبدأ كما هو مخططاً له (مولّد أسئلة بأسلوب الأستاذ)، لكن البنية المعمارية والبيانات تُبنى منذ اليوم الأول بافتراض أن المنتج سيتحول تدريجياً إلى نظام إدارة معرفة المساق. هذا يحوّل المنتج من 'أداة توليد' إلى 'أصل معرفي' يخسره الأستاذ فعلياً إن غادر المنصة — وهذا بالضبط ما يصنع الاحتفاظ بالعملاء (Retention) بالسوق الأكاديمي.
لا حاجة لتغيير الـMVP بسبب هذه الرؤية؛ الحاجة فقط لتصميم قاعدة البيانات والـArchitecture بحيث لا تحتاج إعادة بناء لاحقاً حين تُضاف هذه الطبقات (٥). بهذه النسخة، الجزء الأهم من هذا الأصل المعرفي — بصمة الأسلوب وتحليلات الأسئلة — أصبح له حدود معمارية فعلية عبر محرك ذكاء الأستاذ (٢٩)، لا مجرد نية موصوفة.
## ٣. الميزة التنافسية: أربع طبقات حماية متراكبة
تقييم صريح: بصمة الأسلوب وحدها غير كافية كحاجز تنافسي (خطر ١٥). الحاجز الحقيقي يُبنى من تراكم أربع طبقات، كل طبقة تصعب نسخها أكثر من التي قبلها:
التوصية التنفيذية: الطبقة ١ فقط نشطة بالـMVP (الخطة الفردية، ٢٨). الطبقة ٢ كامنة جزئياً ونشطة جزئياً بالفعل عبر محرك ذكاء الأستاذ (٢٩) — بنيتها التحتية تُبنى من اليوم الأول حتى لو لم تظهر كل مخرجاتها بالواجهة. الطبقتان ٣ و٤ كامنة/مستقبلية (٢٨، ٢٩) تُضافان بعد إثبات المنتج.
## ٤. الهندسة المعمارية الكاملة
### ٤.١ القرار المعماري العام
Modular Monolith، لا Microservices. السبب: فريق من شخص واحد (أو فريق صغير جداً) لا يستفيد من تعقيد تشغيل خدمات مستقلة، بينما يخسر سرعة التطوير والتصحيح. البديل: تطبيق Next.js واحد بحدود Domain واضحة داخلياً (وحدات منفصلة بالكود: courses/, exams/, ai-pipeline/, instructor-intelligence/, billing/, tenants/)، بحيث يمكن لاحقاً فصل أي وحدة إلى خدمة مستقلة إذا أثبت الحمل الفعلي حاجة لذلك — لا قبل ذلك. وحدة instructor-intelligence/ (٢٩) مضافة بهذه النسخة كوحدة نشطة فعلياً، لا كامنة، لأن لها مستهلكاً حقيقياً اليوم (توليد الأسئلة)؛ هذا مختلف عن وحدات الملحق الرابع (قسم/مؤسسة) التي بقيت بلا مجلدات كامنة حصراً.

### ٤.٣ AI Pipeline / RAG Pipeline بالتفصيل
### ٤.٤ المهام الخلفية والطوابير (Background Jobs / Queue)
طابور مهام خفيف الوزن (Supabase Queues أو مكافئ، مع pg_cron للمهام الدورية). كل مهمة تُسجَّل بحالتها مع سياسة إعادة محاولة محدودة (3 محاولات، فاصل متصاعد). الاستثناء الوحيد المسموح باستخدام مفتاح Service Role بالنظام كاملاً هو طبقة queue-consumer تحديداً، وحصراً لقراءة معرّف المستأجر قبل فتح اتصال مقيَّد بذلك المستأجر؛ أي استخدام آخر يُرفض تلقائياً بفحص CI (٨.١، خطر ٢٠).
### ٤.٥ Rate Limiting وAPI Design
Rate Limiting على مستويين: لكل مستخدم ولكل IP. الحدود المبدئية: 5 محاولات تسجيل دخول لكل IP كل دقيقة، 10 طلبات توليد أسئلة لكل حساب كل ساعة بالباقة المجانية، 100 طلب قراءة عام لكل حساب كل دقيقة. تصميم REST داخلي بمسارات واضحة الحدود (/api/courses, /api/exams, /api/style-profiles)، مع توثيق OpenAPI منذ البداية. Webhooks خارجية بنمط Event-Driven غير متزامن (exam.generated).
### ٤.٦ المراقبة والتعافي من الأخطاء
Sentry لتتبع الأخطاء، سجلات مركزية لكل استدعاء ذكاء اصطناعي (المدخل، المخرج، التكلفة، الزمن). Retry Policies: محاولتان قبل التحويل للمزوّد الاحتياطي. Error Recovery: فشل توليد سؤال واحد ضمن دفعة لا يُفشل الطلب كاملاً.
### ٤.٧ منع التكرار عبر Idempotency
كل طلب POST يُنشئ مورداً أو يخصم رصيداً يتطلب ترويسة Idempotency-Key إلزامية (UUID)؛ الخادم يخزّن نتيجة أول طلب لكل مفتاح لمدة 24 ساعة.
## ٥. تصميم قاعدة البيانات
### ٥.١ المبادئ الإلزامية على كل جدول
Row Level Security مفعّل افتراضياً على كل جدول بلا استثناء. Soft Delete عبر عمود deleted_at. Audit Trail موحّد عبر جدول audit_logs مركزي. Versioning لكل كيان قابل للتعديل بعد الإنشاء عبر جدول تاريخ إصدارات منفصل.
### ٥.٢ الكيانات الأساسية
### ٥.٣ الفهرسة والتقسيم (Indexes & Partitioning)
فهارس مركّبة إلزامية على كل عمود tenant_id/organization_id مقترناً بأي عمود يُستخدم بالفلترة المتكررة. تقسيم جدولي audit_logs وprompt_history حسب الشهر منذ البداية. فهرس متجهي منفصل منطقياً لكل مساق، مشروط بتحقق Recall@k فعلي قبل الاعتماد النهائي (تحديث ADR-004).
### ٥.٤ التزامن والتحرير المتزامن (Concurrency)
عمود version رقمي بجدول generated_questions لدعم قفل تفاؤلي. واجهة حل التعارض الفعلية مؤجلة عمداً حتى تفعيل تعدد المراجعين (قدرة كامنة، ٢٨.٢) — العمود موجود من اليوم الأول، الواجهة تُبنى عند الحاجة الفعلية فقط.
## ٦. معمارية الذكاء الاصطناعي
### ٦.١ اختيار النموذج والتكلفة الفعلية
### ٦.٢ تعدد المزوّدين وتفادي Vendor Lock-in
طبقة AI Provider Gateway داخلية: كل استدعاء لنموذج ذكاء اصطناعي يمر عبر واجهة موحدة. Failover تلقائي لمزوّد احتياطي عند فشل المزوّد الأساسي. Cost Optimization: توجيه المهام البسيطة لنموذج أرخص. A/B Testing مستقبلي بين نماذج مختلفة.
### ٦.٣ Prompt Engineering وStructured Output
Prompt Versioning: كل قالب يحمل رقم إصدار، وأي تعديل ينشئ إصداراً جديداً لا يستبدل القديم. Structured Output إلزامي: JSON بمخطط ثابت لكل سؤال (نص السؤال، الخيارات، الإجابة الصحيحة، مستوى الصعوبة المقترح — تُحسب الآن عبر suggestDifficulty بمحرك ذكاء الأستاذ، ٢٩.٣ — والمصدر). JSON Validation عبر Zod أو ما يعادلها.
### ٦.٤ كشف الاختلاق والاستشهاد (Hallucination Detection & Citation)
يعالج هذا القسم الخطر رقم ٢ (الأخطر بالوثيقة). كل سؤال مولّد يحمل استشهاداً إلزامياً ضمن استجابة النموذج نفسها. فحص تحقق آلي (مطابقة المقطع المستشهَد به بمحتوى الصفحة) — هذا المنطق أصبح مملوكاً لمحرك ذكاء الأستاذ عبر scoreCitationConfidence (٢٩.٢، ٢٩.٣)، لا لخطوة مستقلة داخل AI Pipeline كما كان سابقاً. تصنيف ثقة ثلاثي يُعرض للأستاذ، معايَر مقابل الـGolden Dataset (٢٢، ٢٣) قبل عرضه لأول مرة. مراحلة مراجعة بشرية إلزامية: لا اعتماد تلقائي لأي سؤال بأي باقة اشتراك.
### ٦.٥ حلقة التغذية الراجعة (AI Feedback Loop)
كل قرار بشري على سؤال مولّد (قبول/تعديل/رفض) يُسجَّل بـquestion_versions وprompt_history، ليُستخدم لاحقاً بتحسين قوالب الـPrompt وبصمة الأسلوب. هذه البيانات هي بالضبط ما يبني طبقة الحماية التنافسية الثانية (٣)، ونفسها البيانات التدريبية التي تجعل predictDifficulty (إشارة مستقبلية بمحرك ذكاء الأستاذ، ٢٩.٣) قابلة للبناء لاحقاً بلا أي تعديل مخطط.
### ٦.٦ ترحيل نموذج التضمين (Embedding Model Migration)
كل صف بجدول embeddings يحمل عمود embedding_model_version منذ اليوم الأول. عند ترقية النموذج: تشغيل النموذجين بالتوازي مؤقتاً، لا استبدال فوري يكسر الاسترجاع.
## ٧. التكاملات (Integrations)
القاعدة: لا تكامل قبل أن يطلبه استخدام فعلي مثبت. الجدول التالي يرتّب الأولوية؛ التصنيف المعماري الكامل لكل بند (نشطة/كامنة/مستقبلية) موثَّق مركزياً بسجل ٢٨.٢.
## ٨. الأمن الشامل
### ٨.١ المصادقة والصلاحيات
Authentication عبر Supabase Auth، مع تفعيل إلزامي لمصادقة ثنائية لأي حساب مدير مؤسسة. Authorization/RBAC: صلاحيات ديناميكية مخزّنة بقاعدة البيانات. Tenant Isolation: RLS إلزامي على كل جدول، مع فحص CI يرفض أي كود جديد يستعلم قاعدة البيانات متجاوزاً سياسات RLS. الاستثناء الوحيد الموثّق مذكور صراحة بـ٤.٤. فحص CI هذا يُشارك آلياً نفس آلية فحص 'بوابة القدرات' المضافة بـ٢٨.٤/٢٨.٦ — كلاهما امتداد لمفهوم واحد: Architecture Fitness Functions (٢٦).
### ٨.٢ حماية البيانات
Encryption أثناء النقل (TLS) وأثناء التخزين لأي ملف امتحان مرفوع. Secrets Management عبر خدمة أسرار مخصصة. اختبارات اختراق دورية تحاول تجاوز عزل المستأجرين عمداً قبل كل إطلاق ميزة كبرى.
### ٨.٣ أمن الملفات والمدخلات
فحص Magic Bytes لا الامتداد فقط؛ فحص فيروسات لكل ملف قبل معالجته. فصل صارم بالـPrompt بين تعليمات النظام ومحتوى المستند المستخرج، عبر حقل System Prompt منفصل فعلياً عن حقل محتوى المستخدم بكل استدعاء (لا دمج نصي واحد). SQL Injection مستبعد عملياً عبر Prepared Statements.
### ٨.٤ الحماية من إساءة الاستخدام
Rate Limiting على مستوى المستخدم وIP معاً. حظر تدريجي بعد محاولات فاشلة متكررة، وCloudflare كطبقة حماية أمامية.
### ٨.٥ التدقيق والامتثال
Audit Logs: سجل مركزي لكل وصول أو تعديل لبيانات امتحان. GDPR/FERPA وما يعادلهما محلياً: سياسة احتفاظ بيانات موثقة، تصدير/حذف عند الطلب، منطقة استضافة بيانات محددة صراحة. نسخ احتياطي يومي آلي مع اختبار استعادة دوري فعلي.
### ٨.٦ أمان الجلسات وCSRF وXSS
Session Lifecycle: Access Token قصير (ساعة واحدة) مع Refresh Token قابل للإبطال؛ زر 'تسجيل خروج من كل الأجهزة' إلزامي لمدراء المؤسسات. CSRF: Cookies بإعداد SameSite=Lax/Strict + httpOnly + Secure. XSS: تعقيم React الافتراضي؛ dangerouslySetInnerHTML ممنوع بلا استثناء؛ اختبار XSS آلي ضمن Security Tests (٢٢).
## ٩. نموذج العمل
### ٩.١ تقييم الاشتراك الشهري وحده
غير كافٍ كنموذج دخل وحيد. الاشتراك الفردي بسعر منخفض بطيء النمو بالسوق الأكاديمي لسببين: دورة قرار الشراء الأكاديمية طويلة نسبياً، وحجم السوق الفردي محدود مقارنة بالسوق المؤسسي.
### ٩.٢ مصادر الدخل الموصى بها، مرتبة بالأولوية
سوق أسئلة مفتوح بين المؤسسات (Question Marketplace) أُزيل نهائياً من خارطة الطريق لا مؤجلاً فقط — يحمل مخاطر ملكية فكرية جدية (خطر ١٢) لا يمكن تعقيمها بشروط استخدام عادية. القرار محسوم لا مطروحاً للنقاش مستقبلاً، ويبقى مصنَّفاً 'مرفوضة' لا 'مستقبلية' بسجل ٢٨.٢ — التمييز بين الفئتين موضَّح بـ٢٨.٠/٢٨.١. White Label مؤجل أجلاً غير محدد (مستقبلية) لأنه يتطلب حجم مستخدمين كبيراً ليصبح مجدياً.
### ٩.٣ بوابة الدفع (حسم ضروري قبل أي كود، خطر ١٤)
القرار المطلوب مبكراً جداً هو أحد ثلاثة مسارات: بوابة دفع إقليمية بديلة، وسيط تحصيل دولي يقبل التسجيل من المنطقة، أو شريك محلي/إقليمي للتحصيل. طبقة الدفع تُبنى بالكود كـAdapter مجرّد (PaymentProvider interface) منذ البداية.
### ٩.٤ مسار تحصيل بديل بلا بوابة إلكترونية (المرحلة الأولى فعلياً)
أول عملاء مستهدفين مؤسسات لا أفراد؛ مسار التحصيل الفعلي لأول 10–20 عميل لا يحتاج بوابة إلكترونية إطلاقاً: فاتورة مباشرة (تحويل بنكي أو شيك مؤسسي)، بمعالجة يدوية موثّقة (٥.٢). هذا يفصل مخاطرة 'تحصيل الدفع الفعلي' (خطر ٢٢) عن مخاطرة 'تصميم كود مرن' (ADR-007).
## ١٠. خطة الدخول إلى السوق (Go To Market)
القاعدة الصريحة: لا تبدأ بالسوق كله. أول تخصص: الطب والصيدلة. أول دولة: السوق المحلي الذي تملك فيه علاقات مباشرة فعلية (فلسطين تحديداً). أول جامعة/عميل: أستاذ واحد متعاون بكلية طب أو صيدلة. أول قناة تسويق: علاقات مباشرة وتوصية شفهية داخل القسم الأكاديمي، لا إعلانات مدفوعة. التوسع بعد التحقق: من أستاذ واحد إلى قسم كامل (يفتح باب الترخيص المؤسسي الكامن، ٩.٢)، ثم جامعة ثانية، ثم توسع إقليمي.

#### ADR-001: لماذا Modular Monolith لا Microservices؟
المشكلة: كيف تُنظَّم الحدود المعمارية بفريق صغير جداً بمرحلة مبكرة؟
البدائل: (أ) Microservices منذ البداية، (ب) Monolith بلا حدود داخلية واضحة، (ج) Modular Monolith بحدود Domain صريحة.
سبب الاختيار: (ج) — يوفّر سرعة تطوير وتصحيح Monolith العادي، مع حدود داخلية واضحة (١٤.٣) تسمح بفصل أي وحدة لاحقاً بلا إعادة كتابة إن أثبت الحمل الفعلي حاجة لذلك (خطر ١٩).
النتائج: نشر أبسط، تصحيح أخطاء أسهل، تكلفة تشغيلية أقل بالمرحلة المبكرة.
المخاطر: انضباط هندسي مطلوب لمنع تسرّب الاعتماديات بين الوحدات مع الوقت (يُخفَّف بقاعدة ١٤.٣ وفحص CI).
#### ADR-002: لماذا Supabase لا بنية تحتية مُدارة ذاتياً؟
المشكلة: أين تُستضاف قاعدة البيانات والمصادقة والتخزين؟
البدائل: (أ) Postgres/Auth/Storage مُدارة ذاتياً، (ب) Firebase، (ج) Supabase.
سبب الاختيار: (ج) — يجمع Postgres (يدعم RLS وpgvector أصلاً) مع مصادقة وتخزين جاهزين، وخبرة سابقة مثبتة تقلل زمن البناء والمخاطر.
النتائج: تكلفة بداية شبه معدومة، سرعة بناء أعلى.
المخاطر: اعتماد على مزوّد واحد للبنية التحتية — مخفَّف جزئياً بكون Postgres قياسياً وقابلاً للترحيل نظرياً.
#### ADR-003: لماذا Claude كمزوّد ذكاء اصطناعي أساسي؟
المشكلة: أي مزوّد نموذج لغوي يُعتمد لمهمتي بناء بصمة الأسلوب والتوليد؟
البدائل: (أ) OpenAI GPT، (ب) Gemini، (ج) Claude.
سبب الاختيار: (ج) — جودة عالية بمهام الفهم اللغوي الدقيق، مع توفر Sonnet 5 وHaiku 4.5 بفارق تكلفة واضح يخدم استراتيجية التدرّج (٦.١).
النتائج: جودة توليد عالية منذ المرحلة الأولى.
المخاطر: Vendor Lock-in — مخفَّف عبر AI Provider Gateway (٦.٢).
#### ADR-004: لماذا pgvector لا قاعدة بيانات متجهية مخصصة؟
المشكلة: أين تُخزَّن وتُفهرس متجهات الـEmbeddings؟
البدائل: (أ) Pinecone، (ب) Weaviate، (ج) pgvector داخل Postgres نفسه.
سبب الاختيار: (ج) — يتجنب مزامنة بيانات بين قاعدتين، ويستفيد من RLS نفسه المطبَّق على باقي الجداول مباشرة على جدول Embeddings.
النتائج: بساطة تشغيلية، اتساق معاملاتي.
المخاطر: أداء pgvector عند نمو حجم البيانات قد يقل عن حلول متخصصة — مخفَّف بالتقسيم المنطقي لكل مساق (٤.٣).
#### ADR-005: لماذا REST لا GraphQL للواجهة البرمجية؟
المشكلة: أي نمط واجهة برمجية يُعتمد للاستخدام الداخلي والعلني لاحقاً؟
البدائل: (أ) GraphQL، (ب) REST.
سبب الاختيار: (ب) — أبسط للتوثيق والتخزين المؤقت والفهم من عملاء خارجيين، ولا حاجة فعلية لمرونة GraphQL بهذا الحجم.
النتائج: توثيق OpenAPI قياسي، منحنى تعلّم أقل.
المخاطر: أقل مرونة لاستعلامات معقدة جداً — يُعالَج لاحقاً بنقاط نهاية مجمّعة عند الحاجة.
#### ADR-006: لماذا RLS على مستوى قاعدة البيانات لا التفويض على مستوى التطبيق فقط؟
المشكلة: أين يُطبَّق عزل المستأجرين؟
البدائل: (أ) منطق تفويض بالتطبيق فقط، (ب) RLS على مستوى قاعدة البيانات كخط دفاع أول.
سبب الاختيار: (ب) — خط دفاع لا يعتمد على تذكّر كل مطوّر إضافة فحص العزل يدوياً؛ الثغرة الأخطر (خطر ٧) هي نسيان فحص كهذا بمسار واحد منسي.
النتائج: أمان بنيوي لا يعتمد على انضباط بشري متكرر.
المخاطر: تعقيد إضافي بصيانة سياسات RLS — مقبول مقابل ضمان العزل.
#### ADR-007: لماذا يُبنى مسار تحصيل دفع يدوي مؤسسي موازٍ لبوابة الدفع الإلكترونية بمرحلة MVP؟
المشكلة: كيف تُحصَّل مدفوعات المشتركين الأوائل بسياق يصعب فيه الوصول المباشر لبوابات دفع قياسية؟
البدائل: (أ) الانتظار حتى حل بوابة كاملة، (ب) Adapter كودي فقط بلا مسار بديل، (ج) مسار تحصيل يدوي مؤسسي موازٍ + Adapter لاحقاً.
سبب الاختيار: (ج) — يفصل مرونة الكود (حُلّت بـAdapter) عن مشكلة تشغيلية أعمق: وجود مسار تحصيل يعمل أصلاً اليوم.
النتائج: إمكانية تحصيل فعلي من أول يوم عمل بلا انتظار حل بوابة معقد.
المخاطر: معالجة يدوية لا تتوسع تلقائياً — مقبولة صراحة لأول 10–20 عميل فقط.
#### ADR-008: لماذا يُقبل خطر Race Condition بفحص UsageLimit صراحة بمرحلة MVP؟
المشكلة: فجوة زمنية بين فحص الحد بواجهة API وتنفيذه الفعلي بالـWorker.
البدائل: (أ) فحص ذري ثانٍ لحظة المعالجة، (ب) قبول الخطر صراحة مع المراقبة.
سبب الاختيار: (ب) — احتمال تزامن دقيق ضئيل عملياً بحجم 500 مستخدم متزامن، والأثر الأقصى محدود.
النتائج: نطاق MVP أبسط بلا تأخير.
المخاطر: قد يُستغَل بحجم استخدام أعلى — يُعاد تقييمه عند تجاوز 500 مستخدم أو أول دليل استغلال فعلي.
#### ADR-009: لماذا تُؤجَّل معايير إمكانية الوصول (WCAG) لمرحلة Enterprise؟
المشكلة: هل يُلتزَم بمعايير a11y منذ بناء الواجهة الأولى؟
البدائل: (أ) التزام كامل بـWCAG AA منذ اليوم الأول، (ب) تأجيل الالتزام الرسمي حتى مرحلة Enterprise، مع أساسيات فقط الآن.
سبب الاختيار: (ب) — جمهور MVP لا يفرض هذا تعاقدياً بعد، وبرنامج امتثال كامل يستهلك وقتاً غير متناسب مع الأثر بهذه المرحلة.
النتائج: نطاق MVP يبقى مركّزاً على المخاطر الأعلى أثراً.
المخاطر: أي صفقة مؤسسية مبكرة تشترط WCAG تعاقدياً قد تتطلب عملاً إضافياً غير مخطط.
الثلاثة التالية (ADR-010 إلى ADR-012) مضافة بالنسخة ٤.٠.
#### ADR-010: لماذا Feature-Flag Gating لا فصل معماري فعلي للقدرات الكامنة؟
المشكلة: كيف تُبقي القدرات الكامنة (قسم/مؤسسة/فريق/API/تعدد مراجعين) حاضرة معمارياً بلا زيادة تعقيد التنفيذ الحالي؟
البدائل: (أ) بناء الوحدات والجداول كاملة الآن معطّلة بالواجهة فقط، (ب) عدم توثيق أي شيء عنها الآن، (ج) نقاط امتداد خفيفة + بوابة قدرات مركزية واحدة.
سبب الاختيار: (ج) — يحقق مبدأ العمارة التطوّرية: البديل (أ) يكرر خطأ خطر ١٩ على مستوى الوحدات المؤسسية؛ البديل (ب) يخاطر بإعادة هيكلة كاسرة لاحقاً.
النتائج: تعقيد MVP الحالي = تعقيد خطة فردية بحتة + طبقة Gate خفيفة. لا Migration كاسر متوقع عند التفعيل.
المخاطر: طبقة الـGate نقطة فشل واحدة إن نُسي استدعاؤها — يُخفَّف بفحص CI مخصص (٢٨.٦).
#### ADR-011: متى تُصنَّف قدرة كامنة (Dormant) بدل مستقبلية (Future)؟
المشكلة: بلا قاعدة حاسمة، يميل أي فريق لتصنيف كل شيء كامناً أو كل شيء مستقبلياً، وكلاهما يخالف مبدأ العمارة التطوّرية.
البدائل: (أ) قاعدة زمنية (خارطة الطريق)، (ب) قاعدة شعبية (طلب عميل)، (ج) قاعدة بنيوية: هل يمس تأجيل القدرة كياناً جذرياً قائماً بما يفرض Migration كاسر أو إعادة تصميم؟
سبب الاختيار: (ج) — القاعدتان (أ) و(ب) لا تقيسان الكلفة الهندسية الفعلية للتأجيل؛ القاعدة (ج) تربط القرار مباشرة بها، وهي نفس القاعدة الضمنية المستخدمة أصلاً بتصميم ١٤.٢ وعمود version (٥.٤).
النتائج: أي قدرة جديدة تُصنَّف عبر سؤال واحد صريح بدل نقاش ذاتي متكرر — سجل ٢٨.٢ هو التطبيق العملي.
المخاطر: قد يتغيّر تصنيف قدرة مع الوقت — يُعاد تقييم السجل عند أي تغيير جذري بالكيانات الأساسية، لا دورياً تعسفاً.
#### ADR-012: لماذا محرك ذكاء مستقل بدل تضمين المنطق داخل وحدة Assessment؟
المشكلة: أين يجب أن يعيش منطق بصمة الأسلوب وثقة الاستشهاد واقتراح الصعوبة؟
البدائل: (أ) إبقاؤه داخل Assessment كما هو ضمنياً، (ب) بناء منصة ذكاء اصطناعي عامة الآن بكل الاستهلاكات الستة، (ج) استخلاص سياق محدود مستقل الآن بثلاث إشارات نشطة فقط، مع عقد ثابت لبقية الإشارات.
سبب الاختيار: (ج) — البديل (أ) يربط الحاجز التنافسي الحقيقي (طبقة ٢ بـ٣) بمصير ميزة واحدة ويخالف §١٤.٣؛ البديل (ب) يخالف مبدأ العمارة التطوّرية (ADR-011): خمسة من ستة استهلاكات بلا نطاق أو بيانات معرَّفة بعد.
النتائج: مجلد وحدة جديد نشط اليوم (مبرَّر بمستهلك فعلي)، بعقد يتّسع للمستقبل دون بناء أي شيء غير مطلوب الآن.
المخاطر: خطر تجريد سابق لأوانه إن ظل توليد الأسئلة المستهلك الوحيد للأبد — مخفَّف بحصر التنفيذ الفعلي بثلاث إشارات فقط.
## ٢٨. نطاق التنفيذ الفعلي وتصنيف القدرات المستقبلية معمارياً
توضيح مسبق لمنع الخلط: التصنيف (نشطة/كامنة/مستقبلية) بهذا القسم يقيس نضج قدرة اشتراك/خطة تجارية — وهو محور مختلف عن تصنيف نضج قدرات الذكاء الاصطناعي بالقسم ٢٩ (نفس أسماء الفئات، محوران مستقلان عمداً).
الفلسفة الحاكمة لهذا القسم: تفضيل العمارة التطوّرية (Evolutionary Architecture) على التنفيذ المبكر غير المبرَّر. أي قدرة مستقبلية تُمثَّل بنقاط امتداد (Extension Points) أو واجهات (Interfaces) أو سياقات محدودة (Bounded Contexts) أو مفاتيح تفعيل (Feature Flags) — لا بمنطق تشغيلي فعلي. الفرق الجوهري بين 'كامنة' و'مستقبلية': هل تأجيل القدرة بالكامل دون أي امتداد معماري الآن يفرض لاحقاً إعادة تصميم كاسرة لكيان جذري قائم فعلاً؟ إن كانت الإجابة نعم فهي كامنة؛ إن كانت لا فهي مستقبلية فقط (اتساقاً مع خطر ١٩، وقاعدة §٧: 'لا تكامل قبل أن يطلبه استخدام فعلي مثبت').
### ٢٨.٠ ملاحظة تعارض مع قرار سابق — سوق الأسئلة (Marketplace)
سوق الأسئلة (Marketplace) لا يُصنَّف 'مستقبلية' رغم أنه قد يبدو كذلك ظاهرياً. فئة 'مستقبلية' تعني نية بناء لاحقة مؤجلة بلا امتداد معماري الآن؛ أما Marketplace فقرار محسوم بعدم البناء إطلاقاً (§٩.٢)، لمخاطر ملكية فكرية لا يمكن تعقيمها. لذلك يبقى مصنَّفاً ضمن فئة رابعة منفصلة: 'مرفوضة نهائياً' (Rejected) — لا حدود معمارية، لا نقاط امتداد. إعادة فتح هذا القرار تتطلب ADR جديداً صريحاً يُبطل القرار الأصلي، لا إدراجاً ضمن قائمة القدرات المستقبلية.

### ٢٨.٣ الخطة الفردية كحالة خاصة من Organization
القرار الوارد بـ١٤.٢ (Subscription مملوكة لـOrganization مباشرة، لا لمستخدم فردي) هو ما يجعل تصنيف القدرات أعلاه إلى كامنة بتكلفة شبه معدومة ممكناً أصلاً.
عند تسجيل أستاذ جديد، يُنشأ Organization تلقائياً بعضو واحد (Personal Organization) بدور Owner عبر Membership واحد.
عمود plan_code على organizations يُضبط افتراضياً على 'PERSONAL' عند الإنشاء.
لا واجهة 'دعوة عضو' مفعّلة بالمرحلة الحالية — القدرة موجودة بالمخطط أصلاً (تخدم Team Workspace الكامنة).
الترقية لاحقاً من فردي إلى قسم/مؤسسة تعني تفعيل قدرة كامنة موجودة أصلاً، لا بناء نموذج بيانات جديد.
### ٢٨.٤ طبقة بوابة القدرات (Capability Gate)
plans (code, is_active boolean, config jsonb) — صف واحد فعّال حالياً: PERSONAL.
capability_registry (key, display_name_ar, status ∈ {active, dormant, future, rejected}, min_plan_code, depends_on_tables, activation_note).
Middleware واحد بطبقة API: requireCapability(key) يرفض أي وصول لقدرة كامنة بـHTTP 404 لا 403 — إخفاء وجود القدرة كلياً.
### ٢٨.٥ الأثر على قاعدة البيانات
القدرات الكامنة فقط تحصل على امتداد فعلي الآن: organizations.plan_code، organizations.is_personal، generated_questions.version، وجدولا plans وcapability_registry.
القدرات المستقبلية لا تحصل على أي عمود أو جدول الآن مهما كانت قريبة بخارطة الطريق.
أي تفعيل مستقبلي لقدرة كامنة = Migration إضافي متوافق خلفياً، لا Migration كاسر.
### ٢٨.٦ الأثر على بنية الوحدات
لا تُنشأ مجلدات وحدات جديدة الآن لقدرات كامنة أو مستقبلية (لا /modules/department, لا /modules/enterprise).
القدرات الكامنة تحصل على واجهة كود (PlanPolicy + enum PlanCode) بلا تنفيذ فعلي لغير PERSONAL.
القدرات المستقبلية لا تملك أي تمثيل بالكود إطلاقاً — الفارق العملي الحاسم بين Dormant وFuture.
فحص CI يرفض أي Pull Request يضيف مساراً لقدرة dormant دون بوابة القدرات، ويرفض أي مسار لقدرة future أو rejected إطلاقاً.

## ٢٩. محرك ذكاء الأستاذ (Instructor Intelligence Engine)
توضيح مسبق لمنع الخلط: التصنيف هنا يقيس نضج قدرة ذكاء اصطناعي (هل للمحرك منطق فعلي يخدمها؟) — محور مختلف عن تصنيف §٢٨ (خطط الاشتراك). المحرك نفسه بنية تحتية عامة غير مرتبطة بخطة اشتراك بعينها.
### ٢٩.٠ إعادة التموضع: من بيانات متراكمة سلبياً إلى نظام فرعي له عقد إخراج
§٣ حدّد أن الطبقة الثانية من الحماية التنافسية (ذاكرة المساق، تحليلات الأسئلة) هي الحاجز الحقيقي طويل الأمد. هذا القسم يُصعِّد بصمة الأسلوب وما حولها إلى سياق محدود مستقل فعلياً: أي وحدة استهلاك مستقبلية يجب ألا تحتاج قراءة جداول Assessment الداخلية مباشرة — امتداداً لقاعدة §١٤.٣ الصريحة.
المحرك لا يستبدل AI Pipeline (§٦) — الأخير يبقى البنية التحتية الميكانيكية. المحرك يقف فوقها منطقياً: يستهلك مخرجاتها وأحداث التغذية الراجعة البشرية (§٦.٥، §١٧)، وينتج إشارات ذكاء تربوي دائمة قابلة للاستعلام عبر عقد واحد ثابت.
### ٢٩.١ ملاحظة توضيح افتراض — 'توصيات المساق' (Course Recommendations)
§١٥.١ ينص صراحة أن 'لا طلاب بهذا السياق مطلقاً'. 'توصيات المساق' بمعناها الشائع تفترض وجود طالب، وهذا يتعارض مع القرار المحسوم. لذلك يُفسَّر البند هنا بمعنى موجّه للأستاذ: توصية محتوى/بنك أسئلة ذي صلة عبر مساقات الأستاذ أو القسم. إن كان المقصود فعلاً توصيات لطلاب، فهذا يتطلب إعادة فتح قرار §١٥.١ صراحة بـADR جديد.
### ٢٩.٢ الحدود المعمارية: سياق محدود جديد 'ذكاء الأستاذ والمساق'
تمييز عملي: AI Pipeline بنية تحتية ميكانيكية بلا فهم دلالي. Analytics مقاييس منتج/عمل عامة. Instructor Intelligence هو الوحيد الذي 'يفهم' نمط الأستاذ وجودة الأسئلة تربوياً.

وحدة Assessment تستدعي المحرك عبر العقد حصراً — لا قراءة مباشرة لجدول style_profiles.
## ٣٠. ملخص تحديثات النسخة ٤.٠
هذا القسم هو سجل التغيير الرسمي لهذه النسخة، مطلوب صراحة كخاتمة توثّق أثر كل تعديل على الوثيقة ككل.
### ٣٠.١ ملخص التغييرات المعمارية
حصر نطاق التنفيذ الفعلي بالخطة الفردية (Personal Plan) فقط، مع تصنيف معماري ثلاثي إلزامي (نشطة/كامنة/مستقبلية) لكل قدرة اشتراك مستقبلية (قسم أكاديمي، مؤسسة، مساحة عمل فريق، API علنية، تعدد مراجعين)، وفئة رابعة منفصلة (مرفوضة) لسوق الأسئلة تحديداً — القسم ٢٨.
استخلاص محرك ذكاء الأستاذ (Instructor Intelligence Engine) كسياق محدود مستقل بعقد إخراج موحّد (IInstructorIntelligenceEngine)، بدل معالجة بصمة الأسلوب وتحليلات الأسئلة كبيانات تتراكم ضمنياً داخل وحدة توليد الأسئلة — القسم ٢٩.
إضافة طبقة بوابة قدرات مركزية (Capability Gate) واحدة تخدم كلا التصنيفين أعلاه بآلية موحدة (جدولا plans وcapability_registry + Middleware واحد)، بدل فحوصات متناثرة بكل Controller.
نقل ملكية جدول style_profiles البرمجية من وحدة Course Management إلى وحدة Instructor Intelligence الجديدة (لا تغيير على الجدول نفسه أو بياناته).
إضافة عمود واحد Nullable (generated_questions.bloom_level) كنقطة امتداد رخيصة تمنع Migration كاسر لاحقاً عند بناء تصنيف بلوم الكامل (V3).
توحيد منطق فحص ثقة الاستشهاد (Citation Confidence) واقتراح الصعوبة خلف عقد محرك ذكاء الأستاذ بدل خطوتين منفصلتين داخل AI Pipeline.
### ٣٠.٢ الأقسام المعدَّلة
الأقسام غير المذكورة أعلاه (١٠، ١٢، ١٣، ١٨، ٢١، ٢٤) بلا تغيير جوهري — أُعيد إنتاجها بهذه النسخة للحفاظ على وثيقة واحدة متماسكة فقط، لا لأن قراراتها تغيّرت.
### ٣٠.٣ سجلات القرارات المعمارية الجديدة
### ٣٠.٤ المفاضلات المعمارية (Architectural Trade-offs)
لا قرار بالأقسام ٠–٢٧ الأصلية أُلغي أو انعكس بهذه النسخة — كل تعديل مذكور أعلاه هو توسعة أو ربط تبادلي (Cross-Reference)، لا نقض. القرارات المحسومة صراحة (استبعاد Marketplace §٩.٢، عدم وجود طلاب بالنظام §١٥.١) بقيت محسومة، واستُخدمت فعلياً كقيود توجّه تصميم القسمين الجديدين ٢٨ و٢٩ بدل أن تتعارض معهما.

| API Tests | كل نقطة نهاية REST مقابل العقد الموثّق (٢٥) | مع كل Pull Request |
| Database Tests | صحة القيود، الفهارس، سياسات RLS | مع كل Migration |
| Prompt Tests / AI Regression Tests | مقارنة مخرجات كل إصدار قالب جديد بمجموعة بيانات مرجعية | قبل أي نشر لتعديل قوالب Prompt |

| Citation Validation Tests | تحقق آلي أن كل استشهاد بالـGolden Dataset يطابق محتوى الصفحة | مع كل تعديل بمنطق التحقق (يخص محرك ذكاء الأستاذ الآن، ٢٩) |
| Hallucination Tests | قياس نسبة الأسئلة بمعلومة غير موجودة أصلاً بالمصدر | قبل كل نشر لإصدار جديد من قالب التوليد |
